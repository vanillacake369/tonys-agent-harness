# 핵심 원칙 (10개)

## 1. 서술체 일관

- `~다`, `~이다`, `~된다`, `~한다`, `~없다`, `~수 있다` 중심
- 종결을 *인위적으로* 변주하지 않는다. 사실의 시제와 양상에 따라 자연스럽게 결정한다
- 동일 종결 5문장 연속은 단조롭다 — 그러나 회피를 위해 의도적으로 회고형 `~었다/았다` 같은 voice 변주를 강제하지 않는다

## 2. 비유·감각 표현 전면 금지

본문에서 다음 카테고리의 표현을 사용하지 않는다.

| 카테고리 | 금지 예 | 권장 대안 |
|---|---|---|
| 시각 비유 | "흐릿하다", "선명해진다", "또렷해진다" | "정리되어 있지 않다", "명확하게 드러난다" |
| 촉각 비유 | "손에 잡힌다", "쥐어준다", "걸린다" (걸림 의미) | "이해된다", "확인된다", "차단된다" |
| 무게·탄성 비유 | "묵직하다", "단단하다", "굳건하다" | "신뢰성이 높다", "안정적이다" |
| 동작 의인화 | "못 박는다", "켜진다" (한 줄로 켠다), "내려친다" | "단정한다", "활성화된다", "적용된다" |
| 압축 격언 | "이름은 X, 알맹이는 Y", "X 가 말해주는 것은 단순하다", "이 한 줄을 잘못 외워두면…" | 평이한 사실 진술로 풀어 쓴다 |
| 마법·우주·실체 | "마법", "정수", "실체", "본질" (격언 톤), "블랙박스가 아니게 된다", "비로소", "드디어" | 삭제하고 바로 사실 |

## 3. 메타·자기지시 문장 금지

다음 패턴은 작성하지 않는다.

- "이 글에서는 ~를 다룬다"
- "지금까지 ~를 봤지만…"
- "결론적으로", "정리하자면"
- "이 사실이 의미하는 바는 크다"
- "X 가 말해주는 것은 단순하다"
- "이제 ~ 알아보자", "~ 알아볼 차례이다"
- "사족이지만", "여기서 잠깐"

예외: 다음 세 자리에서만 메타 표현 허용
- Why 도입부 *글의 약속* 한 줄 ("이 글은 ~ 를 정리한다")
- `## 들어가며` 절의 *학습 경로 선언* ("이 글은 세 겹의 추상으로 정리한다")
- Remark 의 *요약 표 도입* 한 줄 ("본문에서 다룬 N 주제를 표로 요약한다")

## 4. 1인칭 경험 — Why / Remark 절에 한정

- Why 도입부 1-2 문장 — "필자는 ~ 겪었고 ~ 정리했다"
- Remark 마무리 1-2 단락 — 글을 정리한 뒤의 회고와 운영 관점 논평
- **본론 (What/How) 의 모든 H2 절에 1인칭 회고 금지** — "처음엔 ~인 줄 알았다", "한참 헤맸다" 류 X

본론에서는 *독자 시점 가정 깨기* 는 OK: "직관적으로는 X 라고 가정하기 쉽다 — 그러나 실제는 Y 다".

## 5. 데이터·코드·표 중심

본론 절의 표준 흐름:

1. 주장 한 문장
2. 코드 인용 (Stripe 식 3단: 전 1줄 / 인라인 `// ← 설명` 1-3개 / 후 1줄)
3. 표 또는 Mermaid
4. 결과 정리 한 문장

비유로 설명하지 않는다. 코드/표/사실로 설명한다.

## 6. 인과 표현 — 절제하여 사용

- 명시적 인과 ("X 때문에 Y", "X 라서 Y", "X 가 Y 를 결정한다") 는 *필요한 곳에* 사용한다
- 매 절 끝에 인과적 다리 ("이 미해결은 다음 절의 입력이 된다") 를 *강제하지 않는다*
- 가벼운 다리 한 줄 ("다음 절에서 본다") 는 글 전체에 1-2회만 사용
- 절제된 인과는 백서 voice 의 자연스러운 호흡을 만든다

## 7. 헷지 표현 금지

- "아마", "어쩌면", "혹시", "생각된다", "~인 듯", "~일 수 있다" (불확실 회피 용도)
- 모르는 것은 모른다고 사실로 쓴다: "RFC 는 이를 명시하지 않는다", "공식 문서가 없다"

## 8. 호명·aside 금지

- "여러분", "우리" (독자 호명) — 실습에서 "~가 보이는가?" 같은 자문은 허용
- "사족이지만", "여기서 잠깐", "참고로" 같은 곁가지 prefix — 제거하고 바로 본문

## 9. 한 단락 한 아이디어

- 단락 내 문장은 빈 줄 없이 이어 쓴다
- 단락 간에만 빈 줄 한 개
- 단락 길이 2-5 문장 권장, 최대 6 문장
- 새 개념은 단락당 1개만 도입하고 즉시 코드/표/예시로 구체화

## 10. 본문 이모지 — H2 끝에 한 개만

- H1 / H3 이하 헤더에 이모지 X
- 한 H2 에 이모지 1개
- 본문 (헤더 외) 에 이모지 X
- 추상 이모지 (✨, 🚀, 💡, 🤔) 보다 *내용 특화* 이모지

자세한 이모지 선택 분류는 `/blog-korean` 본문의 "H2 헤더 끝의 이모지" 절을 따른다.

## 11. 보조 설명 박스 — GitHub Alert Syntax 권장

어려운 용어·곁가지 풀이는 본문에 직접 늘어놓지 말고 GitHub Alert Syntax 로 *분리* 한다.

```
> [!NOTE]
> **AEAD 암호화란**
>
> Authenticated Encryption with Associated Data. 암호화와 동시에
> 무결성 검증 태그를 생성하여 변조를 탐지하는 방식.
```

지원 키워드: `NOTE`, `TIP`, `IMPORTANT`, `WARNING`, `CAUTION`. 의미별로 분리해 사용한다.

- `NOTE` — 추가 정보, 용어 풀이
- `TIP` — 권장 사항, 모범 사례
- `IMPORTANT` — 놓치면 안 되는 핵심
- `WARNING` — 흔한 함정·실수
- `CAUTION` — 운영상 위험·되돌릴 수 없는 조작

규칙:
- 한 절당 최대 2-3개 (남용 시 본문 가독성 저하)
- 첫 등장 용어를 *인라인 한 줄로 풀어주는 게 부족할 때만* NOTE 사용
- NOTE 박스 안에는 H2/H3 헤더 사용 X — 박스 첫 줄 `**용어**` 형식으로 강조

### 11-a. 첫 등장 용어 NOTE 박스 배치 기준

첫 등장 약어·전문 용어가 인라인 한 줄 풀이로 충분하지 않을 때 NOTE 박스로 분리한다. 배치 우선순위는 다음과 같다.

1. 그 용어가 *핵심 의사결정* 이 일어나는 문단 직전 (최적)
2. 첫 수식 / 코드 블록 직전
3. 절 진입부 (1, 2가 멀면)

분리 판단 기준:

- 3글자 이상 약어 (PVID, AOF, OCSP, EDH 등) 의 첫 등장 — NOTE 박스 권장
- 인라인 한 줄로 '이해' 는 되지만 후속 문단에서 그 용어의 *옵션 / 메커니즘 / 트레이드오프* 를 깊이 다룬다면 — NOTE 박스로 분리
- 단순 일회성 등장 — 인라인 유지 (예: "VLAN (Virtual LAN) 은 ..." 식)
- 같은 절에서 같은 용어가 두 번째 등장 — 박스 X (첫 등장 한정)

## 12. 매 H2 절 도입부 브릿지 (1-2 문장) — 권장

각 H2 절의 *첫 1-2 문장* 으로 직전 절 결과를 짧게 회수하고 이번 절 주제를 한 문장으로 선언한다.

연결사 지침: *그렇다면*, *그 위에서*, *이번 절은*, *문제는* 같은 자연스러운 연결사를 사용한다. "앞서 X 를 살펴보았다" 류의 형식적 분석체는 피한다.

```
✅ 도입 브릿지 (앞 절의 비대칭 키 → 이번 절의 핸드셰이크)
"앞서 비대칭 키의 동작 방향을 확인했다. TLS 는 이 방향성을
핸드셰이크 단계에서 어떻게 사용하는가."

✅ 본론으로 진입
"핸드셰이크의 목적은 두 가지다. 첫째, ..."
```

"매 절 *끝* 인과 다리 강제 금지" (원칙 6) 와 충돌하지 않는다.

- 끝 다리는 메타 문장이 누적되어 글이 무거워진다 → 강제 X, 글 전체 1-2회만
- 시작 브릿지는 절의 *호흡* 을 잡아준다 → 매 H2 권장

브릿지는 *짧게* — 한 문장이 가장 자연스럽다. 길어지면 메타 누적과 같은 문제.

**과잉 적용 방지**: 5개 H2 절에 동일 브릿지 곡선이 반복되면 정형화로 분류된다. "앞 절에서 X 했다 → 그러면 이번 절은 Y 다" 같은 동일 형식이 3회 이상 등장하면 절반은 브릿지를 *삭제하고* 본론 첫 사실로 곧장 진입한다. 글 한 편 안에서 브릿지 있는 절과 없는 절의 비율은 대략 3:2 정도가 자연스럽다.

### 12-a. 개념 진입 브릿지 — 질문형 연결

새 용어·자료구조·알고리즘·운영 도구를 소개하기 전에는 독자가 왜 그 개념을 필요로 하는지 먼저 제시한다. 사전식 정의로 시작하지 않고, 직전 문제를 해결하려면 무엇을 알아야 하는지 한 문장으로 연결한다.

권장 패턴:

- "`X` 를 판단하려면 무엇을 먼저 확인해야 할까?"
- "`Y` 를 데이터로 저장하려면 어떤 단위로 나눠야 할까?"
- "`Z` 비용을 줄이려면 어느 단계에서 비용이 생기는지 확인해야 한다."
- "이 요청을 처리하려면 애플리케이션 밖에서 어떤 일이 일어나는지 봐야 한다."

이 패턴은 글 전체에 양념처럼 사용한다. 모든 절을 질문으로 시작하면 문체가 기계적으로 보이므로, 핵심 개념이 처음 등장하는 위치에만 둔다.

## 13. mermaid 우선 케이스 — 표보다 시각 직관성이 큰 경우

표보다 mermaid 가 *방향성 / 계층 / 시간 흐름* 을 직관적으로 보여주는 케이스는 mermaid 우선.

| 케이스 | mermaid 타입 |
|---|---|
| 메시지 시퀀스 (프로토콜, RPC) | `sequenceDiagram` |
| 신뢰 사슬, 의존성, 객체 관계 | `classDiagram` 또는 `flowchart` |
| 상태 전이 (라이프사이클) | `stateDiagram-v2` |
| 데이터 흐름 (파이프라인) | `flowchart LR` |
| 클래스 계층 | `classDiagram` |

표가 적합한 경우는 *항목별 비교* (TLS 1.2 vs 1.3 식). 두 방식이 모두 가능할 때는 mermaid 우선.

기본 제약 (`/blog-korean` 의 mermaid 절): 글당 3-7개 권장, 노드 텍스트 3줄 이내, `<` `>` 는 `&lt;` `&gt;` escape.

### 13-a. mermaid 직후 산문 풀이 — 필수

mermaid 다이어그램은 *그림만으로 끝내지 않는다*. 직후 한 단락이 *그림의 어느 노드 / 엣지에서 어떤 결정이 일어나는지* 를 산문으로 풀어야 한다.

풀이 단락의 패턴:

- **flowchart**: "X 노드에서 Y 분기가 일어난다"
- **sequenceDiagram**: "단계 N 에서 Z 값이 정해진다"
- **stateDiagram**: "A → B 전이 조건은 ~"

방향·시점 구분 예:

- "입장 시 — PVID 로 태깅"
- "송출 시 — 태그 제거 여부 결정"

풀이 단락 없이 다음 절로 넘어가면 검토 대상. mermaid 의 *시각 직관성* 과 산문의 *명시적 결정 포인트* 가 결합되어야 그림이 백서 voice 안에서 기능한다.

## 14. 개념 설명 + 사용 시점·사례 페어 룰

절 본문이 *정의 + 메커니즘* 만 있고 "언제 / 어떻게 쓰는지" 가 빠지면 결손으로 분류한다.

각 메커니즘·옵션·기능 설명에는 다음 중 하나를 *1-2 문장* 으로 함께 둔다.

- 사용 시점: "이 메커니즘은 X 상황에 사용된다"
- 사용 환경: "Y 환경에서는 활성화하는 것이 표준이다"
- 실제 사례: "Z 프로젝트에서는 N 으로 운영한다"
- 결정 기준: "A 와 B 중에서는 ~ 일 때 A 를 선택한다"

```
❌ 개념만:
"OCSP Stapling 은 서버가 CA 의 OCSP 응답을 미리 받아 핸드셰이크에
첨부하는 방식이다."

✅ 개념 + 사용 시점/사례:
"OCSP Stapling 은 서버가 CA 의 OCSP 응답을 미리 받아 핸드셰이크에
첨부하는 방식이다. 매 연결마다 CA 까지의 추가 왕복을 절감하고
클라이언트 IP 의 CA 노출을 막는다. nginx 에서는 `ssl_stapling on`
한 줄로 활성화되며, Let's Encrypt 인증서를 사용하는 대부분의 운영
환경에서 기본값으로 켜둔다."
```

특히 *트레이드오프* 절 (성능 vs 보안, 가용성 vs 정합성) 에서는 위 룰이 강제. 단순 개념 나열은 결손.

## 15. 분석 산문 voice — 압축보다 풀어쓰기

본 voice 의 *세부 결* 을 결정하는 룰. 백서 voice 안에서도 *압축적 분석체* 와 *풀어쓴 분석 산문* 의 두 가지가 존재한다. 본 명세는 후자 (분석 산문 voice) 를 표준으로 한다.

### 분석 산문 voice 의 다섯 결

| 결 | 압축 백서 voice (피한다) | 분석 산문 voice (표준) |
|---|---|---|
| 문장 연결 | 대시 `—` 로 두 문장 한 호흡에 묶기 | 마침표로 두 문장 분리 |
| 강조 | 본문 italics `*X*` 빈번 사용 | 본문 italics 회피, "특히 ~" 부사 또는 평이 평서문 |
| 분석어 | "추적", "투입", "산출물", "회수", "zoom-in", "정의된다" | "사용된다", "처리한다", "만든다", "보여준다", "확인한다" |
| 평서문 패턴 | "X 가 Y 인지 추적해본 적 없다" | "X 가 어떤 Y 를 어떤 Z 를 통해 어떻게 W 하는지" 3중 의문문 평서형 |
| 호흡 | 짧고 압축, 한 호흡 마무리 | 약간 풀어쓴 산문, 입말에 가까운 자연스러움 |

### Before → After 사례

**사례 1 — italics + 압축어**

- Before: "다만 명령어가 *어떤 핸드셰이크 단계에서 어떤 산출물을 만드는지* 끝까지 추적해본 적이 없었다 — 개인키, 공개키, CSR, 인증서가 TLS 프로토콜의 어디에 투입되는지 모호한 상태였다."
- After: "다만 명령어가 어떤 데이터를 어떤 프로세스를 통해 어떻게 인증 처리를 하는지 실질적인 원리와 직접적인 사용을 해본 적이 없었다. 특히 개인키, 공개키, CSR, 인증서가 TLS 프로토콜의 어디에서 사용되고 어떻게 사용되는지 모호한 상태였다."

**사례 2 — 대시 묶기 → 마침표 분리**

- Before: "거시 그림의 핸드셰이크 단계에서 *비대칭 키* 가 등장한다 — 왜 필요한지부터 본다."
- After: "거시 흐름에서 핸드셰이크 단계에 비대칭 키가 등장한다. 비대칭 키가 왜 필요한지부터 정리한다."

**사례 3 — 압축 단정 → 풀어쓴 의문문 평서형**

- Before: "TLS 는 OSI 의 특정 계층 번호에 대응시키지 않는다."
- After: "TLS 가 OSI 의 어느 계층 번호에 정확히 대응되는지를 RFC 가 명확하게 정의하지는 않는다."

### 적용 범위와 예외

- 적용 범위: 모든 H2/H3 절 본문의 *서술 단락*
- 예외 1 — **NOTE/WARNING/TIP/IMPORTANT/CAUTION 박스 안**: 압축이 박스의 본래 역할이므로 italics 와 대시 모두 허용
- 예외 2 — **코드/표/mermaid/footnote/이미지 캡션/H2/H3 헤더**: 손대지 않음
- 예외 3 — **단순 bullet list** ("SSL 1.0: 폐기됨", "TLS 1.0: 1999년" 같은 사실 나열): 압축 형태 그대로

### 점검 기준

- [ ] 본문 단락에 italics `*...*` 강조 0건 (NOTE 박스 안 제외)
- [ ] 본문 단락에 대시 `—` 두 문장 묶기 0건 (보조 부연이 한 호흡으로 가는 경우만 1-2회 허용)
- [ ] 압축 분석어 ("추적/투입/산출물/회수") 가 발견되면 풀어쓰기 후보
- [ ] 한 호흡 25 단어 초과 → 두 문장 분리 검토
- [ ] 단정 문장 ("X 가 Y 한다") 보다 *과정 설명* 문장 ("X 가 어떤 방식으로 Y 하는지") 의 비율이 높음

## 16. 주제 몰입 — 회고성 배경과 시리즈 안내 제거

개별 글은 독자가 현재 주제에만 집중하도록 작성한다. 면접 준비, 홈랩 재현, 이전 대화 피드백, 작성 과정, 시리즈 진행 상황은 해당 글의 직접 주제가 아니면 제거한다.

금지 패턴:

- "면접에서 물어볼 수 있다", "면접 준비 과정에서"
- "홈랩에서 재현했다", "재현 환경에서는"
- "다음 글에서는", "다음으로 이어질 주제는", "후속 주제"
- "이번 Phase", "이전 피드백", "작성 세션"

예외:

- 글의 주제 자체가 면접 준비 방법이면 면접 맥락을 사용한다.
- 글의 주제 자체가 배포 환경 구축이면 환경 설명을 사용하되, "운영 검증" 과 "로컬/실험 검증" 을 명확히 분리한다.

## 17. 개념 배열 금지 — 문제 해결 흐름으로 설명

어려운 주제는 키워드를 사전식으로 나열하지 않는다. 먼저 어떤 문제가 있고, 그 문제를 해결하기 위해 어떤 구조가 도입되었으며, 그 구조 내부에서 어떤 처리가 일어나는지 순서대로 설명한다.

권장 흐름:

1. 관찰 가능한 문제 또는 잘못된 판단
2. 그 판단이 합리적으로 보이는 이유
3. 실제 시스템이 문제를 나누는 단위
4. 내부 처리 순서
5. Java / Spring / 운영 판단으로 연결되는 지점
6. 작은 검증 방법

용어 설명은 이 흐름 안에 배치한다. `virtual address`, `page table`, `TLB` 처럼 뒤에서 반복 사용되는 용어도 "정의 → 다음 정의" 순서로 늘어놓지 않는다. 주소 변환이나 요청 처리처럼 실제 동작하는 경로 안에서 용어를 소개한다.

## 18. Bottom-up 우선 — 데이터와 실행 경로에서 출발

개념이 여러 계층에 걸친 글은 top-down 분류표로 시작하지 않는다. 독자가 직접 관찰할 수 있는 입력, 데이터, 요청, 프로세스, 쿼리 결과에서 출발해 한 단계씩 내부 구조를 드러낸다.

권장 전개:

1. 실제 입력 또는 관찰 가능한 결과를 제시한다
2. naive 한 판단이나 구현을 먼저 둔다
3. 측정·검증·반례로 문제가 생기는 지점을 확인한다
4. 그 문제를 해결하기 위해 필요한 개념을 이름 붙인다
5. 내부 구조와 처리 순서를 설명한다
6. 더 나은 구현 또는 운영 판단으로 갱신한다
7. 작은 테스트·벤치마크·EXPLAIN·로그로 확인한다

주제별 적용 예:

- GIS: "feature" 같은 이미 아는 분류어보다 위치를 데이터로 저장하려면 공간 데이터와 속성 데이터를 어떻게 나눠야 하는지에서 시작한다.
- Linux / JVM / Spring: Java 프로그램도 Linux process 로 실행된다는 사실에서 시작하고, virtual memory 와 scheduler 개념을 process 실행 경로 안에서 소개한다.
- 알고리즘: 최적 알고리즘을 먼저 선언하지 않는다. naive 구현의 시간·공간 비용을 측정한 뒤 병목을 줄이는 자료구조를 도입한다.
- 멀티 모듈: 레이어 강제보다 변경 경계, 의존성 방향, 빌드 경계, 런타임 분리 가능성에서 시작한다.

top-down 구조가 필요한 경우에도 먼저 bottom-up overview 를 제공한다. 이후 표는 독자가 이미 본 문제를 분류하는 용도로만 사용한다.

## 19. 실습 배치 — 계층별 작은 확인 후 종합 검증

모든 실습을 글 말미에 몰아넣지 않는다. 계층이 바뀌거나 중요한 판단 기준이 등장하면 해당 절 말미에 작은 확인 방법을 둔다. 마지막 `# How?` 는 여러 절의 판단을 하나로 묶는 종합 검증에 사용한다.

권장 배치:

- 개념 절 말미: 단위 테스트, 작은 SQL, 단일 명령어, 작은 fixture
- 성능 절 말미: JMH, EXPLAIN, profiler, metrics 중 해당 주장에 맞는 도구
- 운영 절 말미: 로그, `pg_stat_statements`, dashboard query, smoke check, rollback 확인 항목
- 종합 How: DBMS 에서 데이터를 꺼내 파싱하고 비즈니스 로직에서 처리하는 end-to-end 실습

도구 이름만 나열하지 않는다. 무엇을 검증하고 어떤 결과가 나오면 주장이 맞는지까지 쓴다.

# 글 구조 (공통)

본 명세를 따르는 글은 다음 H1 골격을 가진다.

```
# Why?

(4단계 구조 — 아래 "Why? 도입 4단계" 절 참고)

# What?

## 들어가며 — [학습 경로 요약] 🗺️

(mermaid 또는 표 기반 구조 + 각 겹 의미 풀이 + 본문 진행 순서)

## [절 제목] [이모지]
...

# How?

## [실습 또는 종합 검증] [이모지]
...

# Remark

(요약 표 1개 + 핵심 사실 정리 + 1인칭 경험/운영 논평)

# Reference

[^X1]: ...
```

`# 끝맺음` 대신 `# Remark` 를 사용한다. Remark 는 단순 요약이 아니라 *글을 정리한 뒤의 회고 + 운영 관점 한마디* 를 포함한다. "다음 글", "후속 주제", "이어지는 주제" 같은 시리즈 안내 문장은 쓰지 않는다.

## Why? 도입 4단계

`# Why?` 는 다음 4단계로 구성한다 (옵션 A — 개념 정리·튜토리얼 글).

1. **1인칭 동기** 1-2 문장 — 어떤 상황에서 무엇을 알고 싶었나
2. **bullet 질문 3-4개** — "그런데 막상 정리하려 하니 모르는 것이 많았다." 직후, 독자가 공감할 구체 질문
3. **답의 윤곽** 1 문장 — "답은 세 개의 추상에 있다 — A, B, C." 또는 "답은 ~ 의 한 줄 설계 결정에 있다."
4. **글의 약속** 1 단락 — 이 글이 어느 순서로 무엇을 정리하는지

bullet 질문은 독자가 공감하는 *구체 질문* 이어야 한다. "왜 배워야 하는가" 수준의 추상 질문은 금지.

> **옵션 B — 문제 해결형 글**: 주제가 구체 기술 문제 해결이라면 `/blog-korean` 의 "가정 설정 → 자연스러운 설계 → 문제 발견 → 문제 명명 → 약속" 5단 내러티브를 사용한다. bullet 4단계는 개념 정리·튜토리얼 성격에 더 자연스럽다.

## `## 들어가며` 절 — What? 진입 직전

`# What?` 직후 첫 H2 로 `## 들어가며 — [학습 경로 한 줄] 🗺️` 를 둔다. 다음 세 요소를 포함한다.

1. **mermaid 또는 표 기반 다이어그램** — 글의 추상 계층 / 세 겹 / 세 경로를 한 눈에 보여줌
2. **각 겹의 의미 풀이** — 위에서 아래로 / 앞에서 뒤로 갈수록 무엇이 깊어지는지 한 단락
3. **본문 진행 순서** — 어떤 H2 가 어느 겹을 다루는지 괄호 풀이로 명시

들어가며 절이 없으면 독자가 글 전체 지도 없이 개별 H2 를 각자 맥락 없이 읽게 된다. 정적 비교는 표, 방향·흐름·계층 전이는 mermaid 를 선택한다. ASCII 박스는 렌더링 품질이 낮아지기 쉬우므로 사용하지 않는다.

# 안티패턴 — Before → After 표

본 명세 위반 사례와 권장 수정.

| 안티패턴 | Before | After |
|---|---|---|
| 시각 비유 | "처음 정리할 때 가장 흐릿했던 X 가 비로소 손에 잡혔다" | "X 가 정리되니 명령어들이 각자의 자리에 들어왔다" |
| 격언 압축 | "이름은 SSL, 알맹이는 TLS — 이 어긋남이 입문자를 혼란스럽게 만든다" | "실제 프로토콜은 TLS 이지만 표기는 SSL 로 통용되는 상태다" |
| 동작 의인화 | "ssl_stapling on; 한 줄로 켠다" | "ssl_stapling on; 한 줄로 활성화된다" |
| 메타 요약 | "표가 말해주는 것은 단순하다 — 1.3 은 옵션을 끄집어내 버렸다" | "TLS 1.3 의 설계 방향은 안전하지 않은 선택지를 표준에서 제거하는 것이다" |
| 본론 1인칭 | "(What 절 본문) 처음엔 RSA 방향을 거꾸로 외웠다. 한참 헤맸다." | (본론에서 삭제. Remark 에서 1인칭으로 한 단락 회고) |
| 매 절 인과 다리 강제 | (모든 H2 끝에 "다음 절에서는…" 형식 다리) | 가벼운 다리는 글 전체에 1-2회만 |
| 헷지 | "아마 이 부분은 ~ 일 것이다" | "RFC 는 이를 명시하지 않는다" |
| 매 절 동형 Tension → Resolution | (모든 H2 가 "통념 → 반례 → 실제 구조" 같은 곡선) | 절마다 다른 리듬 (연표, 표 비교, 시퀀스, 라이프사이클) |
| Why bullet 부재 | (도입 2 문장 후 바로 본론) | bullet 질문 3-4개 + "답은 ~ 세 추상에 있다" 한 줄 |
| 들어가며 절 누락 | (What 직후 첫 H2 가 본론) | `## 들어가며 — 학습 경로` 절 + mermaid 또는 표 + 진행 순서 |
| Diagram 설명 부재 | (mermaid 직후 다음 절로 점프) | 직후 한 단락 — "X 에서 Y 결정" 한 줄 명시 |
| NOTE 박스 위치 오류 | (절 끝 한 줄 박스) | 의사결정 문단 직전 배치 |
| H2 브릿지 약함 | "다음으로 본다" / "이어서 본다" | "앞 절에서 X 를 확인했다. 그 위에서 Y 를 본다." |
| 키워드 나열식 전개 | "`virtual address`, `page table`, `TLB` 를 차례로 정의한다" | "프로세스가 주소를 읽을 때 어떤 변환이 필요한지에서 시작하고, 변환 경로 안에서 용어를 소개한다" |
| 최적해 선제 선언 | "이 문제는 세그먼트 트리로 해결한다" | "naive 구현의 조회 비용을 측정한 뒤, 어떤 반복 계산을 줄여야 하는지 확인하고 자료구조를 선택한다" |
| 주제 밖 배경 | "면접 준비 중 이 질문을 받았다" / "홈랩에서 재현했다" | 글의 직접 주제가 아니면 삭제하고 현재 기술 문제로 바로 진입 |
| NOTE 렌더링 뭉침 | `> [!NOTE]` 직후 본문을 한 줄로 이어 씀 | `> [!NOTE]` + `> **제목**` + 빈 quote 줄 + 본문 |

- [ ] 비유 카테고리 (시각/촉각/무게/의인화/격언) 0건
- [ ] 메타 자기지시 문장 0건 (Why 약속·Remark 요약 도입 제외)

- [ ] 각 H2 끝 이모지 1개, H1/H3 이모지 0개
