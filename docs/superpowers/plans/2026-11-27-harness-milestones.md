# Harness 개선 마일스톤

기준은 `main@e746612333f6d9ea4b0d47719198c19638d7c3ed`이다. 작업 트리는 `main`과 같은 부모 아래에 둔다. M1을 `ee34c94`로 보존한 뒤,
로컬 `main@23efdd0`을 작업 브랜치에 통합했다. 이후 마일스톤은 통합 기준 위에서 진행했다.

## 진행 방식

1. **AS-IS 고정** — 시작 SHA, CLI 진입점, 상태 소유자, 실패 동작을 기록한다. 성능 시나리오는 환경과 입력을 고정해 기준선을 잰다.
2. **TO-BE 합의 기준** — 기존 호출과 데이터의 호환 범위, 새 동작의 관측 결과, 실패 시 보존할 상태를 적는다.
3. **구현** — 합성 fixture의 회귀 테스트를 작성하고 예상한 이유로 실패하는지 확인한 뒤 최소 변경으로 통과시킨다.
4. **AFTER 검증** — 같은 fixture·호스트·표본 수로 재측정한다. 수치 외에 출력 동등성, 실패 처리, 상태 보존을 확인한다. 공개 검증은 `just verify`와 `task core`로 확인한다.
5. **판정** — 통과 여부, 미측정 항목, 다음 단계의 전제와 되돌리는 방법을 남긴다.

## M1. Worktree 도구와 활성 Runtime 관측

| 항목 | AS-IS | TO-BE | 완료 기준 |
|---|---|---|---|
| Worktree | 형제 디렉터리 배치를 수동으로 적용 | `just worktree NAME`으로 기본 체크아웃과 같은 부모 아래 `NAME` 생성 | 로컬 `main`의 기준 커밋을 사용. 이미 있는 디렉터리·링크·브랜치 거부. 원본 편집본 보존 |
| 그래프 | 기본 `config graph`는 원본을 후보로 복사하거나 복호화해 검증. Source 투영은 배포 시 수행 | `harness graph`로 활성 세대에 저장된 그래프 읽기 | 기존 기본 출력 호환. Runtime의 외부 노드·관계 확인. 잠금·키·Vault 없이 조회. 활성 세대 없음과 손상된 그래프는 오류 |
| 성능 | 이전 점검에서 합성 86개 기본 그래프 중앙값 1.56초 | 같은 fixture에서 기존 기본 그래프와 새 Runtime 그래프 비교 | 단일 호스트에서 중앙값 90% 이상 단축. 노드·관계 일치 및 기본 조회 성능 함께 기록 |

- Worktree 실행 파일은 `dev/worktree-create.sh`, 진입점은 `justfile`, 배치 규칙은 `AGENTS.md`에 둔다. `TestWorktreeCreate`는 합성 Git 저장소에서 실제 도구를 실행한다.
- CLI는 명령에 따라 로컬 선언 또는 활성 Runtime을 선택한다. `core`는 활성 세대의 스키마 v3 그래프를 파싱하고 기존 필터·렌더러를 사용한다. `TestRuntimeGraphCLI`는 활성 그래프, 조회 오류, 상태 보존을 CLI에서 확인한다.
- 배포 포맷과 Capability ID를 보존한다. 이 변경을 되돌릴 경우 기존 `config graph`로 조회한다.

### M1 검증 결과

macOS arm64 Apple M4와 Go 1.27.3에서 BEFORE/AFTER 실행 파일을 같은 옵션으로 빌드했다.
하나의 Tool을 모든 Skill이 `hints`로 참조하는 합성 fixture를 8·86개 노드로 만들었다.
BEFORE 바이너리로 `config init`과 `apply`를 실행한 뒤, 같은 Vault와 활성 세대에서 세 명령을 교차 실행했다.
워밍업 1회 이후 각 5회 wall time의 중앙값이다.

| 노드 수 | BEFORE 기본 조회 | AFTER 기본 조회 | AFTER 활성 Runtime 조회 |
|---|---:|---:|---:|
| 8 | 145.03ms | 147.14ms | 3.66ms |
| 86 | 1,340.15ms | 1,350.31ms | 3.60ms |

기본 조회 JSON은 BEFORE/AFTER 바이트 단위로 일치했다. 합성 fixture의 Runtime 조회도 노드 ID·종류와 edge가 같았다.
86개 fixture에서 활성 Runtime 조회는 기존 기본 조회 기준 99.73% 단축됐다.
기본 조회는 여전히 후보 전체를 검사하므로 활성 Runtime 조회와 상태 범위가 다르다.
실제 활성 세대에서도 86개 노드, 75개 edge, 외부 34개를 조회했다. 실제 활성 세대에서 지연 시간은 측정하지 않았다.

`just verify`, `task core`, 두 회귀 테스트가 구현 시점에 macOS에서 통과했다.
통합 이후의 플랫폼별 결과는 아래 검증 기록을 참조한다.

## M2. 검증기 신뢰 경계와 Vault 저장 경쟁

- **AS-IS** — 실행할 검증기 스크립트는 선택된 체크아웃에서 읽는다. 잠금은 로컬 상태 디렉터리 단위다.
- **TO-BE** — 빌드가 소유하는 검증기를 사용하고, 같은 Vault를 쓰는 저장 경로는 Vault 기준으로 잠근다. 저장 직전에도 기준값을 확인한다.
- **완료 기준** — 체크아웃의 검증 스크립트 파일에 기대지 않고 동일한 검증 결과를 얻는다. 하나의 Vault를 공유하는 두 작업이 경쟁할 때 기존 변경을 덮어쓰지 않고 탈락한 편집본을 보존한다. 암호문에 포맷 이관이 필요한지 먼저 확인한다. 설치/릴리스와 macOS·Linux에서 검사한다.

## M3. DAG와 Capability 구성 일치

- **AS-IS** — DAG 단계별 Capability 참조와 composition 그래프를 따로 관리한다. 스킬별 호출 정확도와 토큰 비용은 미측정이다.
- **TO-BE** — DAG 단계의 참조를 그래프에 반영하고 공통 스키마에서 참조, 분기, 승인을 검사한다. 대표 요청 평가 후 새 스킬의 노출 범위를 결정한다.
- **완료 기준** — DAG 참조 누락 0건. 잘못된 대상·분기·승인 fixture 거부. 고정된 요청 집합에서 선택 정확도, 불필요한 호출, 수행 시간의 전후 결과 기록. `arena`는 기존 핀에서 단일 후보로 평가한다.

## M4. 외부 Source와 릴리스 신뢰

- **AS-IS** — 캐시 내부의 digest 파일과 비교하고, 번들 안의 출처 파일로 외부 스킬을 판단했다. Actions는 태그를 참조했다.
- **TO-BE** — Source 투영기가 출처를 기록한다. 명시적으로 pin할 때 원격의 검토 SHA에서 선택 트리를 가져와
  레지스트리에 `reviewed_tree_sha256`을 기록한다. 캐시와 원격에서 복사된 후보 자체의 digest를 확인한 뒤 투영한다.
  Actions는 기존 태그가 가리키던 전체 커밋 SHA로 고정한다.
- **결과** — `101712c`, `8d70d3c`에서 구현했다. 레지스트리 digest와 일치하는 캐시는 오프라인에서 해석됐고,
  불일치하는 후보는 생성되지 않았다. 공개 pstack의 기존 SHA에서 Architect와 Arena를 임시 레지스트리에
  고정했으며 검토 digest 기록과 `apply --dry-run`을 확인했다.
- **호환·복구** — 기존 SHA 전용 pin도 읽고 기존 활성 세대도 조회할 수 있다. 다시 pin하면 검토 digest가 추가된다.
  Workspace 안의 출처 파일은 로컬 스킬의 분류를 바꾸지 않는다. Source 복구 시 승인된 레지스트리와 재검증할 SHA를 사용한다.

## M5. 사용 패턴 평가와 성능

### Skill 구조 검사

Apple M4, macOS arm64, Go 1.27.3 환경에서 BEFORE `101712c`와 AFTER `39e9651` 실행 파일을 교차 실행했다.
스킬당 Markdown 두 파일을 포함하는 동일한 합성 후보를 사용했다. 워밍업 1회 이후 표본 5개의 중앙값이다.

| 입력 | BEFORE | AFTER |
|---|---:|---:|
| 8개 Skill | 162.64ms | 116.44ms |
| 86개 Skill | 1,538.20ms | 1,070.44ms |

86개 기준 벽시계 시간이 30.41% 감소했다. 계측한 검증 하위 프로세스 호출은 1,204회에서 430회로 감소했다.
YAML과 Markdown 링크를 기존 Python 검증기의 같은 프로세스에서 검사한다.
같은 후보의 `apply --dry-run --format json` 결과는 바이트 단위로 일치했다.
측정에는 외부 네트워크 fetch와 실제 사용자의 스킬 콘텐츠가 포함되지 않았다.

재현 명령은 `python3 dev/measure-apply.py /path/to/before /path/to/after`이다.
측정 도구는 임시 Vault와 공개 파일만으로 구성한 체크아웃을 사용한다.

### 라우팅 평가

Codex CLI 0.169.0의 기본 모델, low reasoning, read-only·ephemeral 세션에서 합성 요청 10개를
조건별 2회 실행했다. 세션별 사용자 설정은 로드하지 않았다. BEFORE는 기존 설명을 근사한 평가용 목록이고,
AFTER는 설계 검토와 Arena 선택 조건을 명확히 나눈 후보 목록이다.

| 측정 | BEFORE 중앙값 | AFTER 중앙값 |
|---|---:|---:|
| 정확한 경로 | 8/10 | 10/10 |
| 불필요한 경로 선택 | 2.5건 | 0건 |
| 실행된 Tool 호출 | 0건 | 0건 |
| 입력 토큰 | 24,638 | 24,693 |
| 출력 토큰 | 150.5 | 96 |
| 세션 시간 | 7.88초 | 6.70초 |

재현 명령은 `python3 dev/eval-routing.py`이다. 지원되는 모델을 고정하려면 `--model ID`를 지정한다.
평가는 설명을 분류하는 실험이다. 실제 작업 성공률, 하위 에이전트 실행 비용, 사용자 Runtime 연결 성능은 미측정이다.
Arena의 격리 후보 구조는 통과했다. 실제 위임 조건과 보조 스킬 의존성은 채택 전에 확인한다.
`mcp-builder`는 사내 MCP 개발 과제가 생기면 그 입력을 기준으로 평가한다.

## 통합 검증 기록

- 기본 브랜치에는 M1 이후 변경을 적용하지 않고 전용 Worktree 브랜치에서 커밋했다.
- macOS arm64에서 `just verify`, `task core`, 설치 fixture와 Go race 테스트가 통과했다.
- Linux arm64의 첫 Nix 검증에서 `just verify`는 통과했고, `task core`의 프로파일링 fixture 세 건이
  `/bin/bash` 경로에 의존해 실패했다. 실행 중인 Bash 경로를 사용하도록 수정한 `e421984`에서
  Linux arm64의 `just verify`, `task core`, 설치 fixture가 모두 통과했다.
- 릴리스 아카이브 네 종을 임시 체크아웃에서 빌드하고 SHA-256을 확인했다.
  macOS·Linux arm64 아카이브의 바이너리로 체크아웃 없이 스킬을 생성하고 검증했다.
- 비공개 편집본과 외부 Source는 임시 후보에서 확인했다. 채택 결정과 활성 Runtime 반영은 각각의 권한 경계를 따른다.
