# Harness 개선 마일스톤

기준은 `main@e746612333f6d9ea4b0d47719198c19638d7c3ed`이다. 작업은 `main`과 같은 부모 아래의 전용 Worktree에서 진행한다. 이번 작업 범위는 M1이다.

## 진행 방식

1. **AS-IS 고정** — 시작 SHA, CLI 진입점, 상태 소유자, 실패 동작을 기록한다. 성능 시나리오는 환경과 입력을 고정해 기준선을 잰다.
2. **TO-BE 합의 기준** — 기존 호출과 데이터의 호환 범위, 새 동작의 관측 결과, 실패 시 보존할 상태를 적는다.
3. **구현** — 합성 fixture의 회귀 테스트를 작성하고 예상한 이유로 실패하는지 확인한 뒤 최소 변경으로 통과시킨다.
4. **AFTER 검증** — 같은 fixture·호스트·표본 수로 재측정한다. 수치 외에 출력 동등성, 실패 처리, 상태 보존을 확인한다. 공개 검증은 `just verify`와 `task core`로 확인한다.
5. **판정** — 통과 여부, 미측정 항목, 다음 단계의 전제와 되돌리는 방법을 남긴다.

### M1 검증 결과

macOS arm64 Apple M4와 Go 1.27.3에서 BEFORE/AFTER 실행 파일을 같은 옵션으로 빌드했다.
하나의 Tool을 모든 Skill이 `hints`로 참조하는 합성 fixture를 8·86개 노드로 만들었다.
BEFORE 바이너리로 `config init`과 `apply`를 실행한 뒤, 같은 Vault와 활성 세대에서 세 명령을 교차 실행했다.
워밍업 1회 이후 각 5회 wall time의 중앙값이다.

| 노드 수 | BEFORE 기본 조회 | AFTER 기본 조회 | AFTER 활성 Runtime 조회 |
|---|---:|---:|---:|
| 8 | 145.03ms | 147.14ms | 3.66ms |
| 86 | 1,340.15ms | 1,350.31ms | 3.60ms |

기본 조회 JSON은 BEFORE/AFTER 바이트 단위로 일치했다. 합성 fixture의 Runtime 조회도 노드 ID·종류와 edge가 같았다.
86개 fixture에서 활성 Runtime 조회는 기존 기본 조회 기준 99.73% 단축됐다.
기본 조회는 여전히 후보 전체를 검사하므로 활성 Runtime 조회와 상태 범위가 다르다.
실제 활성 세대에서도 86개 노드, 75개 edge, 외부 34개를 조회했다. 실제 활성 세대에서 지연 시간은 측정하지 않았다.

`just verify`, `task core`, 두 회귀 테스트가 macOS에서 통과했다.
실제 외부 번들 통합 테스트와 Linux 실행은 이번 검증 범위에 포함되지 않았다.

## M2. 검증기 신뢰 경계와 Vault 저장 경쟁

- **AS-IS** — 실행할 검증기 스크립트는 선택된 체크아웃에서 읽는다. 잠금은 로컬 상태 디렉터리 단위다.
- **TO-BE** — 빌드가 소유하는 검증기를 사용하고, 같은 Vault를 쓰는 저장 경로는 Vault 기준으로 잠근다. 저장 직전에도 기준값을 확인한다.
- **완료 기준** — 체크아웃의 검증 스크립트 파일에 기대지 않고 동일한 검증 결과를 얻는다. 하나의 Vault를 공유하는 두 작업이 경쟁할 때 기존 변경을 덮어쓰지 않고 탈락한 편집본을 보존한다. 암호문에 포맷 이관이 필요한지 먼저 확인한다. 설치/릴리스와 macOS·Linux에서 검사한다.

## M3. DAG와 Capability 구성 일치

- **AS-IS** — DAG 단계별 Capability 참조와 composition 그래프를 따로 관리한다. 스킬별 호출 정확도와 토큰 비용은 미측정이다.
- **TO-BE** — DAG 단계의 참조를 그래프에 반영하고 공통 스키마에서 참조, 분기, 승인을 검사한다. 대표 요청 평가 후 새 스킬의 노출 범위를 결정한다.
- **완료 기준** — DAG 참조 누락 0건. 잘못된 대상·분기·승인 fixture 거부. 고정된 요청 집합에서 선택 정확도, 불필요한 호출, 수행 시간의 전후 결과 기록. `arena`는 기존 핀에서 단일 후보로 평가한다.

M1의 수치와 동작을 먼저 검토한다. M2의 저장 경계 검증을 마친 뒤 M3의 선언 변경을 실제 Runtime 후보에서 확인한다.
